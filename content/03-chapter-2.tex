\section{Реализация движка нагрузочного тестирования}

Центральным компонентом системы Tsunami является \textbf{движок нагрузочного тестирования} --- модуль, отвечающий за генерацию HTTP и gRPC нагрузки с заданной интенсивностью запросов, измерение задержки и сбор агрегированных метрик.
Движок предоставляет две публичные точки входа: функцию \texttt{RunAttack} для автономного запуска и \texttt{RunAttackWithMetrics} для режима реального времени, при котором потребитель передаёт заранее созданный объект метрик и может наблюдать за ними непосредственно в ходе теста.
Разделение на два варианта позволяет использовать одно ядро как в CLI-режиме с живым прогрессом, так и в серверном режиме с WebSocket-трансляцией метрик.
Подобная архитектура соответствует принципу единственной ответственности: движок не знает о способе представления результатов и не зависит от транспортного уровня сервера.

\subsection*{Архитектура резерва исполнителей}

Фундаментом движка служит \textbf{резерв исполнителей} --- классическая модель параллельного выполнения задач на основе каналов языка Go~\cite{gospec}.
При запуске теста создаётся фиксированное число горутин-исполнителей (\texttt{cfg.Workers}, по умолчанию 50), каждая из которых ожидает задания из канала \texttt{jobs}.
Буфер входящего канала рассчитывается по формуле \(\max(\mathit{Workers} \times 2,\; 100)\), что предотвращает простой диспетчера при кратковременном замедлении исполнителей.
Результаты каждого запроса помещаются в канал \texttt{results} ёмкостью \(\mathit{Workers} \times 2\), который параллельно обрабатывает горутина-коллектор, накапливающая статистику в объекте \texttt{GlobalMetrics}.

Управление скоростью генерации нагрузки возложено на \textbf{ограничитель скорости} библиотеки \texttt{go.uber.org/ratelimit}~\cite{ratelimit}, реализующей алгоритм текущего ведра.
Вызов \texttt{rateLimiter.Take()} в горутине блокирует её ровно на время, необходимое для соблюдения целевого RPS, не допуская накопления задержанных токенов и выброса пакетных всплесков.
Диспетчер непрерывно отправляет маркеры в канал \texttt{jobs}; при получении сигнала остановки через канал \texttt{stopCh} он завершает работу, после чего закрытие канала \texttt{jobs} каскадно останавливает все воркеры.
Для защиты от двойного закрытия канала применяется \texttt{sync.Once}, что исключает паническое завершение при одновременном получении внешнего сигнала и истечении таймера длительности теста.

\begin{lstlisting}[caption={Инициализация резерва исполнителей и ограничителя скорости в \texttt{RunAttackWithMetrics}},label={lst:workerpool}]
jobsBufferSize := max(cfg.Workers*2, 100)
jobs    := make(chan struct{}, jobsBufferSize)
results := make(chan RequestResult, cfg.Workers*2)
var wg sync.WaitGroup

for i := uint(1); i <= cfg.Workers; i++ {
    wg.Add(1)
    go worker(client, cfg, jobs, results, &wg)
}
rateLimiter := ratelimit.New(cfg.RPS)
\end{lstlisting}

\subsection*{HTTP-клиент и классификация ошибок}

Каждый исполнитель использует общий экземпляр \texttt{*http.Client}, созданный функцией \texttt{createHTTPClient}.
Транспортный уровень конфигурируется с параметрами \texttt{MaxIdleConns} и \texttt{MaxConnsPerHost}, установленными равными \texttt{cfg.Connections} (по умолчанию 100), что обеспечивает эффективное повторное использование TCP-соединений через механизм \textbf{Keep-Alive}.
Задержка измеряется от момента вызова \texttt{client.Do(req)} до завершения чтения тела ответа функцией \texttt{io.ReadAll}, что даёт корректное время отклика, включающее передачу данных.

Для точной диагностики сбоев каждая ошибка классифицируется функцией \texttt{classifyError}, которая относит её к одному из пяти типов: \texttt{Timeout}, \texttt{ConnectionRefused}, \texttt{DNS}, \texttt{TLS} или \texttt{Other}.
Классификация производится по типу сетевой ошибки (\texttt{net.Error.Timeout()}) и по подстрокам сообщения об ошибке («connection refused», «no such host», «tls», «certificate»).
Запрос считается успешным при \texttt{statusCode < 400}; ответы с кодами 4xx и 5xx регистрируются как отказы без категории сетевой ошибки, поскольку соединение было установлено корректно.
Подобная детализация позволяет пользователю оперативно различить инфраструктурные проблемы (отказ DNS, истёкший TLS-сертификат) от прикладных ошибок сервера.

\subsection*{Сбор метрик и вычисление перцентилей}

Все метрики агрегируются в структуре \textbf{\texttt{GlobalMetrics}}.
Структура встраивает \texttt{sync.Mutex}, что обеспечивает атомарное обновление счётчиков из горутины-коллектора без гонок данных.
Для вычисления перцентилей задержки используется \textbf{кольцевой буфер} ёмкостью \(\mathit{MaxLatencySamples} = 100\,000\) замеров; при размере \texttt{time.Duration} в 8 байт это соответствует приблизительно 800 КБ памяти независимо от длительности теста.
По достижении предела новые значения замещают старые по индексу \texttt{latencyIdx}, инкрементируемому по модулю ёмкости буфера; таким образом обеспечивается ограниченное потребление памяти при неограниченном числе запросов.

Перцентили P50, P90, P95 и P99 вычисляются функцией \texttt{Calculate\-All\-Percentiles}.
Для экономии ресурсов выполняется однократная сортировка среза (функция \texttt{slices.Sort} с асимптотикой $O(n \log n)$), после чего каждый перцентиль определяется по индексу \(\max\!\left(\lceil p / 100 \cdot N \rceil - 1,\; 0\right)\).

\begin{lstlisting}[caption={Функция \texttt{CalculateAllPercentiles} и вспомогательная \texttt{percentileIndex}},label={lst:percentile}]
func CalculateAllPercentiles(latencies []time.Duration) (
    p50, p90, p95, p99 time.Duration) {
    if len(latencies) == 0 { return }
    sorted := make([]time.Duration, len(latencies))
    copy(sorted, latencies)
    slices.Sort(sorted)
    p50 = sorted[percentileIndex(sorted, 50)]
    p90 = sorted[percentileIndex(sorted, 90)]
    p95 = sorted[percentileIndex(sorted, 95)]
    p99 = sorted[percentileIndex(sorted, 99)]
    return
}
func percentileIndex(sorted []time.Duration, p int) int {
    return max(int(math.Ceil(
        float64(p)/100.0*float64(len(sorted))))-1, 0)
}
\end{lstlisting}

\subsection*{Поддержка протокола gRPC}

Помимо HTTP, система поддерживает нагрузочное тестирование по протоколу \textbf{gRPC}~\cite{grpcgo}, реализованное в модуле gRPC-атак.
Вместо единственного \texttt{http.Client} gRPC-исполнители разделяют резерв из \texttt{cfg.Connections} каналов (по умолчанию 4); каждый исполнитель выбирает канал по формуле \texttt{conns[i \% poolSize]}, что обеспечивает равномерное распределение нагрузки между соединениями без дополнительной синхронизации.
Разрешение полного имени метода осуществляется функцией \texttt{ResolveMethod} двумя способами: из предоставленного \texttt{.proto}-файла с помощью компилятора \texttt{protocompile} или через server reflection в режиме реального времени.
Коды ошибок gRPC отображаются на те же пять типов: \texttt{DeadlineExceeded} преобразуется в \texttt{Timeout}, \texttt{Unavailable}~--- в \texttt{ConnectionRefused} и т.\,д., что позволяет использовать единую систему формирования отчётов для обоих протоколов.

\section{Реализация CLI-интерфейса}

Командный интерфейс является основным способом взаимодействия конечного пользователя с системой Tsunami при автономном запуске нагрузочных тестов.
В качестве фреймворка для построения CLI выбрана библиотека \textbf{Cobra}~\cite{cobra} --- де-факто стандарт разработки CLI-инструментов на языке Go, применяемый в таких проектах, как Docker и Kubernetes.
Cobra обеспечивает декларативное описание команд, автоматическую генерацию справочной документации и разграничение флагов на глобальные и локальные, что позволило структурировать интерфейс инструмента в виде иерархии трёх подкоманд с минимальным дублированием кода.
Корневая команда \texttt{tsunami} предоставляет единственный глобальный флаг \texttt{--cpus} для явного задания числа используемых процессорных ядер (\texttt{runtime.GOMAXPROCS}).

\subsection*{Формат задания интенсивности нагрузки}

Ключевым параметром команды \texttt{attack} является флаг \texttt{--rate}, задающий интенсивность нагрузки в формате \texttt{N/Vunit}, где \texttt{N} --- число запросов, \texttt{V} --- числовое значение временного интервала, \texttt{unit} --- единица времени (\texttt{ms}, \texttt{s}, \texttt{m}, \texttt{h}).
Данный формат позволяет задавать как целочисленный RPS (\texttt{100/1s}), так и субсекундные интервалы (\texttt{50/500ms}), не прибегая к вещественным числам, что исключает ошибки округления при вводе.
Разбор строки выполняется функцией \texttt{ParseRateToRPS} посредством регулярного выражения; значения ниже 1 RPS округляются вверх до 1 во избежание деления на ноль в ограничителе скорости.

\begin{lstlisting}[caption={Регулярное выражение для разбора формата rate},label={lst:rate}]
var RateRegex = regexp.MustCompile(
    `^(\d+)/(\d+)(ms|s|m|h)$`)
\end{lstlisting}

\subsection*{Предварительная валидация параметров}

Перед запуском теста хук \texttt{PersistentPreRunE} каждой подкоманды вызывает набор проверок, что обеспечивает информативные сообщения об ошибках ещё до аллоцирования ресурсов движком.
Валидируются следующие условия: URL обязан содержать схему \texttt{http://} или \texttt{https://}; строка rate должна соответствовать регулярному выражению \texttt{RateRegex}; количество воркеров и соединений должно быть больше нуля; тайм-аут запроса должен быть положительным.
Такая схема «fail fast» соответствует идиомам языка Go~\cite{gospec} и избавляет пользователя от необходимости ожидать начала теста, чтобы обнаружить опечатку в параметрах.
Дополнительно проверяется, что значение \texttt{--workers} не превышает допустимого максимума, заданного флагом \texttt{--max-workers}, что предотвращает случайное истощение ресурсов тестирующей машины.

\subsection*{Отображение живого прогресса}

В процессе выполнения HTTP-теста функция \texttt{liveProgress} запускает отдельную горутину с таймером 100\,мс, которая каждые 100 миллисекунд считывает текущее состояние объекта \texttt{GlobalMetrics} и перезаписывает строку терминала через символ возврата каретки \texttt{\textbackslash r}.
Вывод включает анимированный индикатор активности, индикатор выполнения для теста с конечной длительностью, текущий и целевой RPS, а также счётчики успешных и неуспешных запросов.
Цвет индикатора RPS динамически изменяется в зависимости от соотношения фактического и целевого значений: зелёный --- при достижении цели, жёлтый --- при отставании более чем на 10\%, красный --- при отставании более чем на 30\%.
Использование ANSI escape-кодов и таймера с периодом 100 мс обеспечивает плавное обновление без мерцания и без существенного влияния на производительность самого движка.

\subsection*{Корректное завершение работы}

Устойчивость CLI к прерываниям обеспечивается механизмом \textbf{graceful shutdown}, реализованным в CLI-команде \texttt{attack}.
После инициализации теста функция \texttt{signal.Notify} регистрирует обработчик сигналов \texttt{SIGINT} и \texttt{SIGTERM}; при получении любого из них закрывается канал \texttt{stopCh}, что через горутины диспетчера и воркеров ведёт к плавному завершению всех «в полёте» запросов.
Функция \texttt{wg.Wait()} удерживает управление вплоть до завершения последнего воркера, гарантируя, что итоговый отчёт сформируется на полном наборе результатов.
Аналогичная схема завершения применяется в команде \texttt{serve}: сигналы ОС инициируют вызов \texttt{server.Shutdown} с тайм-аутом 10 секунд, после чего сервер перестаёт принимать новые соединения, дождавшись завершения активных запросов.

Таким образом, CLI-интерфейс Tsunami реализован с использованием фреймворка Cobra и предоставляет три специализированные подкоманды с декларативной валидацией параметров, интуитивно понятным форматом задания нагрузки и информативным отображением прогресса в реальном времени.

\section{Реализация серверной части и веб-интерфейса}

Для сценариев, в которых командная строка неудобна или недоступна, система Tsunami предоставляет альтернативный режим взаимодействия через браузер.
Команда \texttt{tsunami serve} запускает HTTP-сервер, предоставляющий REST API для управления тестами, WebSocket-канал для трансляции метрик в реальном времени и встроенное React-приложение в качестве веб-интерфейса.
Все три компонента скомпилированы в единый бинарный файл без внешних зависимостей, что упрощает развёртывание на удалённых серверах и в контейнерных средах.
Серверная часть полностью отделена от движка: серверный компонент зависит от движка нагрузочного тестирования только через публичные интерфейсы, не затрагивая внутреннюю логику резерва исполнителей.

\subsection*{REST API}

Обработчики HTTP-запросов образуют REST API из восьми маршрутов, перечисленных в таблице~\ref{tab:ch2-api}.
Сервер инициализируется с таймаутами \texttt{ReadTimeout: 15s}, \texttt{WriteTimeout: 15s} и \texttt{IdleTimeout: 60s}, что предотвращает утечку ресурсов при медленных или зависших клиентах.
Для разработки клиентской части с отдельного порта (Vite dev server) к каждому ответу добавляются CORS-заголовки, разрешающие запросы с \texttt{localhost:3000} и \texttt{localhost:5173}.

\subsection*{Автомат состояний тестовой сессии}

Управление жизненным циклом теста возложено на структуру \textbf{\texttt{TestSession}} и менеджер \textbf{\texttt{SessionManager}}, реализованные в серверном компоненте.
Система допускает только одну активную сессию одновременно; при запуске нового теста \texttt{SessionManager.createSession} автоматически останавливает текущую, если та находится в состоянии \texttt{running}.
Доступ к полю \texttt{SessionManager.current} защищён через \texttt{sync.RWMutex}, что обеспечивает корректность при одновременных запросах к API.

Жизненный цикл сессии описывается автоматом из пяти состояний: \texttt{idle} (ожидание), \texttt{running} (тест выполняется), \texttt{completed} (успешно завершён), \texttt{stopped} (остановлен по запросу) и \texttt{error} (аварийное завершение).
Переходы осуществляются методами \texttt{Start()}, \texttt{Stop()}, \texttt{Complete()} и \texttt{SetError()}, каждый из которых защищён мьютексом и не допускает недопустимых переходов.
Полный исходный код модуля управления сессиями приведён в приложении~А.

\subsection*{WebSocket-сервер трансляции метрик}

Для рассылки метрик в реальном времени реализован \textbf{WebSocket-сервер} по паттерну «публикация-подписка» с использованием библиотеки \texttt{gorilla/websocket}~\cite{gorilla}.
Структура \texttt{Hub} содержит отображение подключённых клиентов, буферизованный канал \texttt{broadcast} ёмкостью 256 и каналы регистрации/отмены регистрации клиентов.

\begin{lstlisting}[caption={Структура \texttt{Hub} WebSocket-сервера},label={lst:hub}]
type Hub struct {
    clients    map[*Client]bool
    broadcast  chan []byte
    register   chan *Client
    unregister chan *Client
    mu         sync.RWMutex
}
\end{lstlisting}

Сервер рассылает метрики каждые \textbf{50 мс}, формируя сообщения типа \texttt{WSMessage} с полями \texttt{type} (\texttt{metrics}, \texttt{completed}, \texttt{stopped}, \texttt{error}), \texttt{timestamp} и \texttt{data}.
Отправка клиентам реализована в неблокирующем режиме: если буфер отправки клиента (\texttt{Client.send}, ёмкость 256) заполнен, клиент немедленно отключается, что предотвращает блокировку хаба медленными получателями и обеспечивает неограниченную масштабируемость числа подключений.
\texttt{WebSocket Upgrader} разрешает соединения с \texttt{localhost:3000}, \texttt{localhost:5173} и \texttt{localhost:8080}, обеспечивая совместимость как с режимом разработки фронтенда, так и со встроенной раздачей SPA.
Для формализации порядка взаимодействия между браузерным клиентом,
WebSocket-сервером и объектом тестовой сессии разработана диаграмма
последовательности.
Она охватывает полный цикл сценария: от момента установки WebSocket-соединения
до получения клиентом финального сообщения о завершении теста.
Диаграмма последовательности представлена на рисунке~\ref{fig:sequence}.

\subsection*{Встраивание клиентской части в бинарный файл}

Для получения единого самодостаточного исполняемого файла результат сборки React-приложения встраивается в бинарный файл Go с помощью директивы \textbf{\texttt{go:embed}}~\cite{gospec}.
При наличии тега компиляции \texttt{embed\_frontend} скомпилированные статические ресурсы монтируются в корень HTTP-сервера через пользовательский \texttt{SPAHandler}, который перенаправляет все неизвестные маршруты на \texttt{index.html} для корректной работы клиентского роутинга.
Без тега \texttt{embed\_frontend} сервер запускается в режиме «только API», что удобно при разработке фронтенда с горячей перезагрузкой через \textbf{Vite}~\cite{vite}.

\subsection*{React SPA}

Пользовательский интерфейс разработан как \textbf{одностраничное приложение} на платформе \textbf{React 18}~\cite{react} с использованием TypeScript и сборщика Vite.
Визуализация метрик реализована с помощью библиотеки \textbf{Recharts}~\cite{recharts}: линейный график задержки (\texttt{LineChart}), круговая диаграмма распределения статусных кодов (\texttt{PieChart}) и гистограмма ошибок по типам (\texttt{BarChart}).
Стилизация компонентов выполнена посредством \textbf{Tailwind CSS}~\cite{tailwind}; интернационализация обеспечена библиотекой \texttt{i18next}.
WebSocket-клиент поддерживает автоматическое переподключение: при разрыве соединения производится до 5 попыток восстановления с экспоненциальной задержкой по формуле \(\mathit{delay} \times \mathit{attempt}\), что обеспечивает устойчивость к кратковременным сетевым сбоям без ручного вмешательства пользователя.

Пример JSON-отчёта, экспортируемого по завершении теста, приведён в приложении~Г.

В результате серверная часть и веб-интерфейс Tsunami образуют единый самодостаточный бинарный файл, обеспечивающий управление тестами через REST API, мониторинг метрик в реальном времени через WebSocket и браузерный пользовательский интерфейс с поддержкой двух языков.

\section{Тестирование системы}

Обеспечение корректности реализованной системы достигается применением двухуровневой стратегии: \textbf{юнит-тестирование} для изолированной верификации алгоритмов ключевых функций и \textbf{интеграционное тестирование} для проверки взаимодействия компонентов в условиях, максимально приближённых к промышленным~\cite[с.~77]{kulikov2020}.
Все тесты реализованы на стандартном пакете \texttt{testing} языка Go~\cite{gospec}; интеграционные тесты выделены тегом сборки \texttt{integration} и исполняются отдельным шагом конвейера CI с доступным Docker-демоном.
Подобное разграничение позволяет запускать быстрые юнит-тесты при каждом коммите, тогда как дорогостоящие интеграционные тесты выполняются только перед итоговой сборкой.
Такой подход обеспечивает воспроизводимость результатов испытаний.

\subsection*{Юнит-тестирование алгоритма перцентилей}

Наибольшую вычислительную сложность в движке представляет алгоритм расчёта перцентилей, поэтому его тестирование выполнено наиболее тщательно.
Функция \texttt{TestCalculatePercentile} содержит 12 субтестов, покрывающих граничные случаи: пустой срез, единственный элемент, чётные и нечётные наборы, дубликаты, несортированный ввод, а также точные значения P0, P50, P75, P90, P95, P99 и P100 на различных объёмах данных.
Использование табличного подхода (\textit{table-driven tests}) позволяет добавлять новые случаи без дублирования кода вызова, что соответствует идиомам языка Go.

\begin{lstlisting}[caption={Фрагмент юнит-теста \texttt{TestCalculatePercentile}},label={lst:unittest}]
{
    name: "empty slice returns zero",
    args: args{latencies: []time.Duration{}, percentile: 50},
    want: 0,
},
{
    name: "unsorted input is sorted before calculation",
    args: args{
        latencies:  []time.Duration{50*ms, 10*ms, 30*ms, 20*ms, 40*ms},
        percentile: 50,
    },
    want: 30 * ms,
},
{
    name: "p99 on 100 elements",
    args: args{
        latencies: func() []time.Duration {
            d := make([]time.Duration, 100)
            for i := range d { d[i] = time.Duration(i+1) * ms }
            return d
        }(),
        percentile: 99,
    },
    want: 99 * ms,
},
\end{lstlisting}

\subsection*{Интеграционное тестирование с реальным сервером}

Интеграционные тесты используют библиотеку \textbf{testcontainers-go}~\cite{testcontainers} для автоматического запуска Docker-контейнера с сервисом \textbf{httpbin} на порту 8888.
\texttt{httpbin} предоставляет предсказуемые HTTP-маршруты с возможностью задания искусственной задержки ответа (\texttt{/delay/N}), кодов состояния (\texttt{/status/NNN}) и прочих параметров, что позволяет воспроизводить различные сценарии поведения сервера без создания тестовых заглушек.
Подход с реальными контейнерами исключает расхождение между поведением мок-объектов и промышленного сервера, которое является частым источником ложных срабатываний в тестировании на основе заглушек.
Контейнер создаётся и уничтожается автоматически в рамках каждого тестового запуска, обеспечивая полную изоляцию окружения.

Полные листинги интеграционных тестов приведены в приложении~В.
В модуле интеграционных тестов движка реализованы три тестовые функции.
\texttt{TestRunAttack\_BasicSuccess} проверяет базовый успешный сценарий (10 RPS, 2 с, 5 исполнителей, 10 соединений): по завершении теста \texttt{Successes > 0} при \texttt{Failures = 0}.
\texttt{TestRunAttack\_TimeoutClassification} убеждается, что запрос к маршруту с задержкой 3 с при тайм-ауте клиента 500 мс корректно квалифицируется как \texttt{ErrorTypeTimeout}.
\texttt{TestRunAttack\_MetricsAccuracy} содержит три субтеста, проверяющих, что коды 2xx регистрируются как успех, а 4xx и 5xx --- как отказ без дополнительной категории сетевой ошибки.

Тесты серверной части используют пакет \texttt{net/http/httptest} для запуска обработчиков без сетевого стека.
\texttt{TestHandleStartAttack} отправляет POST-запрос на \texttt{/api/attack/start} и проверяет ответ 200 с непустым идентификатором сессии и статусом \texttt{running}.
\texttt{TestHandleStartAttack\_ValidationError} верифицирует возврат кода 400 при отсутствующем URL, некорректной схеме и невалидном формате rate.
\texttt{TestHandleStopAttack} проверяет полный цикл запуска и остановки теста: после остановки теста с длительностью 60 с статус сессии меняется на \texttt{stopped}.

\subsection*{Оценка производительности}

Для верификации нефункционального требования о достижении не менее 1\,000~RPS
при 50 параллельных исполнителях был проведён нагрузочный эксперимент.
В качестве цели использовался Docker-контейнер с сервисом \texttt{httpbin},
запущенный на том же хосте, чтобы исключить сетевые задержки канала
и оценить собственную пропускную способность движка.
Тест выполнялся командой:

\begin{lstlisting}[caption={Команда нагрузочного теста для оценки производительности},label={lst:perftest}]
tsunami attack -u http://localhost:8888/get -r 1000/1s -d 30s -w 50
\end{lstlisting}

Эксперимент повторялся 10~раз, приведённые показатели представляют собой средние значения по всем прогонам.
По итогам 30-секундного прогона зафиксированы следующие показатели:
суммарно отправлено~--- 30\,000 запросов,
успешных ответов~--- 30\,000,
фактическая пропускная способность~--- \textbf{1\,000~RPS}.
Перцентили задержки составили:
P50~---~1~мс, P90~---~1~мс, P95~---~1~мс, P99~---~2~мс,
что подтверждает минимальный накладной расход ограничителя скорости
на основе алгоритма текущего ведра.

Нефункциональное требование к задержке доставки метрик через WebSocket выполняется:
сервер рассылает обновлённые метрики каждые 50~мс,
что вдвое перекрывает установленный предел
без необходимости дополнительных измерений.

В результате тестирования подтверждена корректность алгоритма вычисления перцентилей, точность классификации сетевых ошибок и соответствие REST API заявленным контрактам; все тесты успешно проходят в среде GitHub Actions CI.
Нагрузочный эксперимент верифицировал достижение целевого показателя
производительности~--- более 1\,000~RPS при 50~исполнителях~--- и подтвердил
соответствие инструмента заявленным нефункциональным требованиям.

\section{Сборка, дистрибуция и CI/CD проекта}

Неотъемлемым условием промышленного уровня инструмента является возможность его воспроизводимой сборки для целевых платформ конечного пользователя без ручных зависимостей и настройки окружения.
Для достижения этой цели в проекте Tsunami применяется инструмент \textbf{GoReleaser}~\cite{goreleaser}, автоматизирующий кросс-компиляцию, архивирование артефактов, публикацию релизов на платформе GitHub и обновление Homebrew-формулы.
Весь процесс сборки и публикации параметризован единственным файлом \texttt{.goreleaser.yaml}, полный текст которого приведён в приложении~Б.
Это обеспечивает идентичность локальных и CI-сборок и исключает человеческий фактор при создании релизов.
Использование полностью статической компиляции с \texttt{CGO\_ENABLED=0} означает, что сгенерированный бинарный файл не имеет зависимостей от системных библиотек и может быть запущен на любой совместимой операционной системе без дополнительной установки.

\subsection*{Кросс-компиляция с GoReleaser}

Конфигурация GoReleaser в файле \texttt{.goreleaser.yaml} задаёт матрицу сборки из шести целевых платформ: операционные системы \texttt{linux}, \texttt{darwin} (macOS) и \texttt{windows} в сочетании с архитектурами \texttt{amd64} и \texttt{arm64}.
Тег сборки \texttt{embed\_frontend} активирует встраивание скомпилированного React-приложения через \texttt{go:embed}, а тег \texttt{netgo} принудительно использует встроенные Go-реализации сетевых функций вместо системных.
Через флаги линкера \texttt{-s -w} из бинарного файла удаляются символы отладки и таблицы DWARF, что уменьшает размер артефакта примерно на 30\%.

\begin{lstlisting}[caption={Ключевые блоки конфигурации GoReleaser (\texttt{.goreleaser.yaml})},label={lst:goreleaser}]
builds:
  - binary: tsunami
    env:
      - CGO_ENABLED=0
    goos:   [linux, darwin, windows]
    goarch: [amd64, arm64]
    tags:   [netgo, embed_frontend]
    ldflags:
      - -s -w
      - -X github.com/paniccaaa/tsunami/cmd.Version={{.Version}}
brews:
  - name: tsunami
    repository: {owner: paniccaaa, name: homebrew-tap}
    install: |
      bin.install "tsunami"
\end{lstlisting}

Помимо GitHub Releases, GoReleaser публикует \textbf{Homebrew}-формулу в репозиторий \texttt{paniccaaa/homebrew-tap}, что позволяет пользователям macOS и Linux устанавливать инструмент командой \texttt{brew install paniccaaa/tap/tsunami}.
Архивы для Windows упаковываются в формат ZIP, для остальных платформ --- в TAR.GZ; к каждому релизу прилагается файл контрольных сумм \texttt{checksums.txt} в формате SHA-256.

Рабочий процесс \texttt{ci.yml} запускается при каждой отправке изменений в ветку \texttt{main} и при открытии pull request.
Задачи выстроены в линейную цепочку зависимостей: сначала выполняется \texttt{unit-tests}, затем \texttt{integration-tests}, и лишь после их успешного завершения запускается сборка.
Такой порядок гарантирует, что финальная сборка с встроенной клиентской частью производится только после прохождения всех тестов.
Сборка приложения выполняется с теми же флагами \texttt{CGO\_ENABLED=0}, \texttt{-tags=netgo} и \texttt{ldflags}, что и в релизе, обеспечивая идентичность CI-артефакта промышленной сборке.

Рабочий процесс \texttt{release.yml} активируется исключительно при публикации git-тегов формата \texttt{v*} и выполняет полный релизный цикл: сборку React-приложения, запуск GoReleaser для создания шести платформенных архивов с контрольными суммами и их публикацию на GitHub Releases с автоматическим обновлением Homebrew-формулы.

\subsection*{Контейнеризация}

Для развёртывания в оркестрируемых средах проект содержит многоступенчатый \textbf{Dockerfile}~\cite{docker} для серверной части на базе образа \texttt{golang:1.25-alpine} (стадия сборки) и \texttt{alpine:latest} (стадия среды выполнения), а также отдельный Dockerfile фронтенда на основе \texttt{node:20-alpine} и \texttt{nginx:alpine}.
Файл \texttt{docker-compose.yml} определяет два сервиса (\texttt{backend} и \texttt{frontend}) в изолированной bridge-сети \texttt{tsunami-network}; для бэкенда настроена healthcheck-проверка маршрута \texttt{/health} с интервалом 30 секунд, тайм-аутом 10 секунд и тремя попытками до признания контейнера нездоровым.
Политика перезапуска \texttt{unless-stopped} обеспечивает автоматическое восстановление сервисов после перезагрузки хоста без ручного вмешательства пользователя.

Таким образом, проект Tsunami реализован с полным производственным циклом: от воспроизводимой кросс-компиляции статических бинарных файлов для шести целевых платформ до автоматизированного релизного конвейера с публикацией в Homebrew и поддержкой контейнерного развёртывания через Docker Compose.
